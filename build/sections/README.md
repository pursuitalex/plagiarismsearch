# The Section Library

Ready-made page sections for the CMS. An editor copies a section's HTML from the catalogue
(`site/section-library.html`), changes text, links and a few listed variant values, and it
looks and behaves right — without knowing Tailwind and without copying CSS or JS. Styles
and behaviour live in the shared `site.css` / `tailwind.css` / `site.js`; a page carries
none of its own.

This file is for whoever maintains the library. `DESIGN.md` describes each component's
look; `build/assets/README.md` describes the asset pipeline it is compiled in.

## The registry

`build/sections/index.js` lists every component, in catalogue order. Two tools run that
list and nothing else: the validator (`build/check-library.js`) and the catalogue builder
(`build/section-library.js`). A component that is in the registry is validated and shown.

| Component | `data-component` | Root class | What it is |
|---|---|---|---|
| Hero | `hero` | `.hero` | the tinted first section: H1 and the checker or a diagram |
| Stat rail | `stat-rail` | `.stat-rail` | the thin band of figures and marks under a hero |
| Steps | `steps` | `.steps-section` | a numbered sequence |
| Feature cards | `feature-cards` | `.cards-section` | an unnumbered set of icon cards |
| Sources | `sources` | `.sources-section` | what a check is compared against |
| Report showcase | `report-showcase` | `.report-showcase` | a head, the report (sealed), how to read it |
| Start free | `start-free` | `.start-free` | the two free limits and a button |
| Pricing preview | `pricing-preview` | `.pricing-preview` | a head, the period switch and plan cards (sealed) |
| Reviews | `reviews` | `.reviews-section` | customers quoted: a rail or a grid of cards |
| FAQ | `faq` | `.faq` | the accordion |
| CTA band | `cta-band` | `.cta-band` | the closing band before the footer |
| Banner | `banner` | `.banner` | the compact dark banner |
| Inquiry form | `inquiry-form` | `.inquiry` | a head column beside a form card |

Three **primitives** are hosted by components and are not registry entries: the Section
Header (`section-head.js` / `.css` — pill, h2, intro, quiet link; it reads its host's
ground: `data-bg="white"`, `data-surface="dark"`, `data-accent="teal"`), the Action
(`action.js` / `.css` — `.action-button` with `data-tone="light|ghost|inverse"`,
`.action-link`) and the Icon tile (`icon-tile.js` / `.css` — `.icon-tile[data-tone]`).
`check-tools.js` holds their rules for every host. The pen mark (`.pen-word` >
`svg.pen-mark`) is the hero's and the report showcase's.

## The files of a component

| File | Role |
|---|---|
| `<name>.js` | the template: `section(options)` returns the HTML. Every generator calls it; a hand-written page carries the same markup. Throws on an option the contract does not know |
| `<name>.css` | its styles, written with `@apply`; imported by `build/assets/css/tailwind.src.css` |
| `<name>.contract.js` | the content contract: `variants` (each `data-*` switch, its values, a Ukrainian description), `classes` (what each part may carry), `hooks`, `inline` (tags allowed in a text part), `editable` and `locked` (the two lists the catalogue prints) |
| `<name>.check.js` | the validator's rules, written from the contract with `check-tools.js`; and its self-test: `BAD` (pastes that must be refused) and `GOOD` (edits that must pass), each an edit of a catalogue snippet |
| `<name>.catalogue.js` | the catalogue chapter: its lead, its snippets (each read back from an approved page with `catalogue-tools.js`), the "where used" table |
| `snippets/<name>-*.html` | generated by `build/section-library.js`: one file per approved configuration. Never edited by hand |

Behaviour is never page-local: a component's script is a module in
`build/assets/js/NN-*.js`, hooked on `data-*` (or a hook class such as `rv`, `od-num`).

## The CSS rulebook, in ten lines

1. Write with `@apply`, so every value is the utility's own; the file is compiled in the
   same Tailwind run as the utilities (`tailwind.src.css` imports it between components
   and utilities).
2. Outside `@layer`: a layered rule is dropped when its class is not in `content`, and a
   section that exists only in the CMS would lose its CSS.
3. One class per selector — weight (0,1,0), like a utility. Anything more goes inside
   `:where()`: `:where(.steps-section[data-layout="rail"]) .steps-item`.
4. Variants are `data-*` attributes in `:where()`, never modifier classes.
5. A property is set by a class OR by a utility on the same element, never both: the
   utilities come last and a stray one would silently win.
6. Order decides between equals: a later rule wins, and a later *base* rule beats an
   earlier `@media` rule. A variant therefore restates every breakpoint it changes.
7. No Tailwind utility in the markup an editor copies. A sealed block (below) may keep its
   own.
8. A part carries the gap *above* itself, so it can be removed without leaving a
   neighbour's margin behind. A library block embedded in another component carries no
   utilities; the host spaces it from its own side.
9. Surfaces follow the ground (IMAGES.md § 8.5): on a tint a card is white and its plate
   tint; a pill's background and dot come from the host section, never from the pill.
10. After any class change run `npm run build:assets` before judging anything, and diff
    `site/assets/css/tailwind.css`: a word in `build/sections/*.js` that looks like a
    utility — even inside a string or a comment — makes Tailwind generate it.

## Sealed blocks

What is not editor content is rendered by the template, marked `data-slot="…"`, named in
the contract and copied as it is; the validator does not inspect its classes.

| Slot | Where | What the validator still holds |
|---|---|---|
| `checker` | Hero | the quick-check form is inside; its button returns to the hero's id (a warning) |
| `media` | Hero, Steps, Sources, Report showcase | nothing — a diagram or a block drawn for the page |
| `report` | Report showcase | the report is there and whole (`[data-report]`, its passages and sources). `build/report.js` renders it |
| `pricing-periods`, `pricing-plans` | Pricing preview | **the figures**: the JSON island is there, is the pricing data source's (`build/pricing-data.js`), and every card shows what the island holds for the first period. `build/pricing.js` renders both |

Two components carry facts rather than copy. **Prices** (DEC-0042): plan names, prices,
quotas, periods and the Recommended state come from the data through the island and
`60-pricing.js`; nothing of it is typed into a page, and the validator refuses a price in
the text around the cards. **Reviews**: a card is a quotation of a real review — text,
name and rating as the platform published them; the validator holds the card's shape,
each page's own check holds its words to `build/reviews.js`.

## Adding a component

1. Inventory: `data-component` across `site/*.html` and `build/*.js`. One name may hide
   two families of different structure or intent — split them; look-alikes of
   incompatible structure are a question for the owner, not a variant.
2. Keep each instance's DOM skeleton. Replace utility class lists with semantic classes
   whose `@apply` reproduces them exactly. Where two instances differ: a legitimate
   difference becomes a named `data-*` variant; a drift that paints nothing is removed
   and recorded; a visible one is a question.
3. Write `<name>.js`, `.css` (and import it in `tailwind.src.css`), `.contract.js`,
   `.check.js`, `.catalogue.js`; add the registry entry.
4. Move every generator onto the template; give hand-written pages the same markup
   (their source is the file in `site/`).
5. `npm run build:assets` → the generators → `node build/section-library.js` →
   `node build/shell.js` → `node build/pages.js` → the checks → parity (below).
6. Describe it in `DESIGN.md`, and here in the table above.

## Running the validator

```
node build/check-library.js                    every site/*.html, every snippet, every self-test
node build/check-library.js page.html …        a page, or a fragment saved to a file
node build/check-library.js --stdin < paste    HTML piped in (a CMS paste)
```

Exit code 1 on any error; a warning (an id the script renumbers, a rating whose figure
the script repairs) does not fail. `require('./build/check-library').validate(html)`
returns `{ roots, errors, warnings }`. `design-system.html` is skipped by name: it shows
showcase renditions inside its own frames.

The self-test is part of the default run: each `BAD` entry must be refused, each `GOOD`
entry accepted. A new rule needs both.

## Parity

`node build/parity/run.js <page.html>` compares the page now with the same page at the
last commit (`--ref=<commit>` for another baseline): pixels, every element's box and 65
computed properties, behaviour, the no-JS / reduced-motion states, and each top-level
section alone in an empty page, at 375 / 768 / 1440. `--quick` is 1440 only and no reuse
— for iterating. Run the full one on every page a component touches before committing
it, and commit after each component so the next is measured against a clean baseline.
Two or three runs in parallel are fine; more makes reveal timing flaky.

The target is 0 px and 0 geometry differences. A difference that was *decided* is
recorded in `build/parity/pages.js` against the baseline commit, with its reason and the
exact properties: `acceptAgainst('<commit>', { 'page.html': [['margin-top', …], 'why'] },
'Component: ')`. The run prints it as ACCEPT; anything outside the listed properties
still fails. Never widen an acceptance to make a run pass. Two sections of one
`data-component` on a page are told apart by their ids (`--section=steps.how-to-read`).

## Decisions that are not reopened

- The section rhythm is not unified: `lg:py-28` and `lg:py-32` are both legitimate
  (`data-space="md|lg"`).
- The Ukrainian page's own proportions stay variants.
- A pill's background and dot accent are derived from the host section, never set per
  pill; the Section Header's intro has one size.
- A library block embedded in another component carries no utilities; the host spaces it.
- Anything an editor would have to keep in step by hand (id pairs, aria wiring, a
  rating's figure) is repaired by the component's script at load, and the validator only
  warns.
- Surface alternation (IMAGES.md § 8.5): on a tint section a card is white and its plate
  tint. Where an approved page breaks it, it is listed, not fixed silently.
- Page-specific compositions stay out: the About page's Team card and Timeline
  (`build/about/`), the Reviews pages' walls, marquees and video stage, the Trustpilot
  masonry of the tool pages, the bespoke diagrams (`report-ai-dark`, `results-dark`,
  `source-map`, `storage-map`, `relationship-map`).
